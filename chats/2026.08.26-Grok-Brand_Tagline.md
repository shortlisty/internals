Да, это один из ключевых cost-драйверов продукта.

### Где именно деньги уходят

1. **Хранение**
   - PDF + планы + фото. У агентства 150–300 файлов — это ещё терпимо (десятки–сотни МБ).
   - Но если хранить оригиналы + извлечённые версии + эмбеддинги + превью — объём быстро растёт.
   - При 200 агентствах с активной библиотекой уже легко выходишь на терабайты.

2. **Парсинг / AI-extraction**
   - Это самая дорогая часть.
   - Каждый PDF нужно:
     - распознать (OCR, если скан)
     - понять структуру (таблицы вместимости, политики кейтеринга, AV-спеки, ограничения)
     - вытащить поля в структурированный вид
     - иногда сделать эмбеддинги для поиска
   - При «паре сотен» файлов на агентство и нормальном качестве извлечения стоимость одного прохода может быть ощутимой (особенно если использовать сильные модели).

3. **Повторные обработки**
   - Файл обновили → нужно перепарсить.
   - Улучшили промпты/модели → хочется перепрогнать старую библиотеку.
   - Это уже не разовый cost, а постоянный.

### Как обычно решают, чтобы не сдохнуть по unit-economics

- **Не парсить всё сразу**.  
  Сначала только метаданные + превью. Полный extraction — по требованию или когда площадку реально добавляют в питч.

- **Кэширование и дедупликация**.  
  Один и тот же PDF (особенно популярных площадок) не парсить заново у каждого агентства.

- **Тяжёлые модели — только для сложных документов**.  
  Простые прайс-листы и одностраничные спеки — более дешёвыми моделями / правилами.

- **Лимиты в тарифах**.  
  $150 — N страниц/месяц или N новых документов.  
  $300 — выше лимит + приоритет.

- **Перекладывание части стоимости**.  
  В будущем, когда площадки сами загружают «верифицированные» профили, агентствам почти ничего парсить не нужно.

### Реалистичная картина

При текущих ценах на хранение + LLM-инференс это **управляемо**, но только если:

- не парсить всё подряд агрессивно,
- хорошо следить за повторными обработками,
- и закладывать cost в ценообразование (особенно в $300-тариф и eventual venue-side monetization).

Хочешь, могу прикинуть грубую unit-экономику: сколько примерно будет стоить хранение + один полный проход 200 PDF на агентство при разных подходах (дешёвые модели vs сильные, с OCR и без).

| Чистый PDFBox / iText | Текст + координаты                          | Структуру придётся собирать самому         |

**Главная боль venue-PDF:**

- Таблицы вместимости («Theatre 200 / Banquet 120 / Cocktail 300»)
- Многоколоночные прайс-листы
- Сканы / фото планов этажей
- Разный язык и вёрстка

«Сырой MD без чёткой структуры» почти гарантированно превратит хорошую таблицу в кашу. Qwen потом будет угадывать, а не извлекать.

Лучше на этом этапе уже стараться сохранить хоть какую-то структуру (таблицы как markdown-tables или JSON-ячейки), а не отдавать совсем сырой текст.

### 2. Qwen на VPS

Это самая реалистичная часть схемы.

- **Qwen2.5 / Qwen3 7B–32B** на CPU/GPU VPS вполне тянут extraction.
- Для 8–14B хватает нормального VPS с 16–32 GB RAM (или дешёвой GPU).
- 32B+ уже хочется хотя бы одной нормальной видеокарты.

**Плюсы:**

- Данные никуда не уходят
- Стоимость предсказуемая (фиксированная аренда VPS)
- Можно крутить очередь и батчить

**Минусы:**

- Скорость. На CPU один длинный документ может занимать десятки секунд.
- Качество сильно зависит от того, насколько чистый входной MD.
- Нужно самому делать retry, валидацию JSON, мониторинг очереди, обновление моделей.

### 3. Реалистичная оценка схемы

| Этап                | Оценка                 | Комментарий                              |
| ------------------- | ---------------------- | ---------------------------------------- |
| Стоимость           | Хорошо                 | Существенно дешевле Claude/GPT на объёме |
| Качество extraction | Средне / ниже среднего | Особенно таблицы и сканы                 |
| Скорость            | Средне                 | Зависит от железа и размера модели       |
| Операционка         | Высокая                | Очереди, OCR, мониторинг, fallback       |
| Масштабирование     | Нормально              | Пока агентств немного                    |

### Более практичный гибрид (рекомендую)

1. **PDF → структурированный текст/MD**
   - Сначала пробовать layout-aware open-source (Marker, Docling, MinerU, OpenDataLoader) — даже если это Python.
   - Java оставлять для простого текстового слоя + Tabula на таблицы.
   - Для сканов — отдельный OCR-путь (PaddleOCR / Tesseract + потом LLM).

2. **Extraction**
   - Основной объём → Qwen 14B/32B на своём VPS.
   - Сложные/важные документы (или когда confidence низкий) → более сильная модель через API (как fallback).

3. **Не парсить всё подряд**
   - Полный extraction только когда площадку реально добавляют в питч или по запросу.
   - Остальное — лениво + кэш.

Схема «Java → сырой MD → Qwen на VPS» **жизнеспособна** как cost-saving слой, особенно на старте.

1. **Текст есть** → можно вытащить capacity, цены, политики.

 ├─ 2. Извлечь все картинки + их позицию на странице
