**VenueMi** is a collaborative workspace for event agencies and their clients. It solves the problem of scattered venue files (PDFs, floor plans, price lists in email/WhatsApp/shared drives) by turning them into structured, searchable data and an interactive client pitch that produces a locked, timestamped approved spec. [Raw](https://raw.githubusercontent.com/venuemi/system-design-documentation/dev/docs/README.md)

### Product layers

1. **Personal Venue Catalog** (data layer) — Agency private library. Upload documents → AI extracts capacity (by configuration), catering policy, AV specs, restrictions, contacts, pricing indicators, etc. Searchable and structured.
2. **Digital Sales Room / Deal Workspace** (output layer) — Planner selects venues from the catalog, generates a private interactive pitch board (shareable link, no client login). Client reviews, sets preferences (SHORTLISTED / CONSIDERING / DECLINED), asks questions, and Approves. System locks an immutable snapshot with full event history. [Raw](https://raw.githubusercontent.com/venuemi/system-design-documentation/dev/docs/README.md)

**Target users:** Event agencies (5–50 people), independent planners, corporate event teams.  
**Pricing:** $150/month (full library + pitch board, unlimited members); $300/month (priority processing, API, white-label). Future: venues pay for verified public profiles.

**One-sentence pitch:** VenueMi turns venue files into a pitch and a pitch into an approved spec — so agencies close client briefs in hours, not days.

---

### Architecture overview

VenueMi Intelligence is built **on top of the existing iQ Key Value foundation** (no forks of core services). It reuses gateway, IAM, billing, audit, UI app, and tenancy libraries. [Raw](https://raw.githubusercontent.com/venuemi/system-design-documentation/dev/docs/platform/architecture-overview.md)

**New components:**

- Shared libraries: `mi-data-intelligence` (domain-agnostic extraction, provenance, events) + `mi-venue-model` (venue-specific model, canonical fields, migrations).
- Services: `mi-venue-service` (core domain, sync), `mi-venue-processing-worker` (async ETL, embeddings, aggregation), `mi-mc-loader` (master catalog imports), standalone Node scrapers.
- Infra extensions: pgvector + PostGIS on existing PostgreSQL; optional IBM Docling (Phase 2).

**Tech stack highlights:** Spring MVC + MyBatis (no JPA), RabbitMQ, Liquibase XML, Spring Security OAuth2 (RS256 JWT), schema-per-tenant isolation (`t_{tenantKey}` via `MyBatisSchemaInterceptor` + `TenantContext`), Apache Tika + Spring AI + GPT-4o for extraction, OpenAI embeddings, S3/MinIO.

---

### UI: Venue Management

Shared entity abstraction `AnyVenue` with context discriminator (`"tenant"` | `"master_catalog"`). Same form, components, and canonical `VenueMetadata` JSONB schema for both tenant venues and platform master venues. [Raw](https://raw.githubusercontent.com/venuemi/system-design-documentation/dev/docs/platform/ui-venue-management.md)

- **Guiding principles:** DRY/KISS, schema-driven form (static TS form spec → one registry entry per field), progressive disclosure (SEEDED shows only a few fields), fast list views via flat server-resolved summary DTOs.
- **Profile stages (tenant):** SEEDED → ENRICHED → CURATED → READY.
- **Placement:** Feature-Sliced Design (FSD) addons (`venue-management`) shared between `foundation-ui-app` (tenant) and `foundation-ui-platform-admin`. Tenant-only panels (annotations, quick-fill) suppressed for master catalog.
- Rich metadata covers capacity configurations, catering, AV/tech, accessibility, logistics, outdoor space, exclusivity, restrictions, amenities, contacts, pricing, social, ratings, plus per-field provenance/confidence.

---

### UI: Deal Workspace

Shared planner–client space centered on a `Proposal` (curated venues from the catalog). [Raw](https://raw.githubusercontent.com/venuemi/system-design-documentation/dev/docs/platform/ui-deal-workspace.md)

**Key properties:**

- One shareable link, no client account.
- Bilateral control + immutable append-only event log.
- Progressive workflow (draft → share → review → approve).
- Client-side computed data-confidence score (HIGH/MEDIUM/LOW; client never sees LOW).

**Core entities:** `Proposal` (statuses DRAFT/SHARED/IN_REVIEW/APPROVED/ARCHIVED), `ProposalVenue` (exposed fields + planner/client notes + preference + snapshot), `ProposalEvent` (full audit trail), `ProposalSnapshot` (locked on approve), proposal-scoped colored labels.

**UI structure:** Planner board (header, ordered venue cards with confidence/labels/notes, collaboration sidebar, history drawer) + public client board (`/share/:token`) with preference selector, Q&A, and sticky Approve bar. White-label branding gated by plan entitlement.

**Как правильно создавать Epic, User Stories, Technical Tasks и приоритизировать в VenueMi**

В репозитории VenueMi уже есть чёткая, хорошо прописанная система (см. `docs/roadmap/epics/README.md`, `milestones/README.md`, `feature-checklist.md` и `AGENTS.md` §4.4–4.5). Ниже — практическое руководство, которое полностью соответствует их правилам + классические методы приоритизации (WSJF, RICE, MoSCoW).

### 1. Иерархия артефактов

| Уровень               | Что это                                                 | Единица ценности                                  | Где живёт                             |
| --------------------- | ------------------------------------------------------- | ------------------------------------------------- | ------------------------------------- |
| **Vision**            | Стратегическое направление                              | «Зачем мы это делаем»                             | `vision.md`                           |
| **Epic**              | Кластер связанных user-facing возможностей              | User outcome («As a [role], I can now [outcome]») | `epics/E{N}-{slug}.md`                |
| **Milestone**         | Shippable increment (то, что можно показать end-to-end) | Одна демо-сессия                                  | `milestones/v{X}.{Y}-{slug}.md`       |
| **User Story**        | Конкретное поведение пользователя                       | «As a… I want… so that…»                          | Внутри Epic + в Feature checklist     |
| **Technical Task**    | Конкретная работа инженера (API, схема, компонент)      | Готовый PR / merged код                           | Jira/Linear/GitHub Issues (не в docs) |
| **Feature Checklist** | Плоский приоритизированный список всех user-visible фич | Чекбокс P0–P3                                     | `feature-checklist.md`                |

**Золотое правило VenueMi:**  
Если набор возможностей **нельзя** сформулировать как «As a [role], I can now [outcome]» — это **не Epic**. Разбей или объедини.

---

### 2. Как правильно создать Epic

Строго следуй процедуре из `epics/README.md` (index-first + 9 обязательных секций):

1. **Проверь, что это действительно Epic**
   - Можно ли сказать: «As a [role], I can now [outcome]»?
   - Он может пересекать несколько milestones? (да — это нормально).
   - Не слишком ли он маленький (тогда это Task) или огромный (разбей).

2. **Определи группу и зависимости**
   - Group A — Platform Foundation
   - Group B — Personal Venue Catalog
   - Group C — Digital Sales Room
   - Group D — Post-v1.0

3. **Возьми следующий свободный номер E{N}** и **сначала** добавь строку в индекс `epics/README.md` (статус `Not started`), закоммить, **потом** создавай файл.

4. **Создай файл `E{N}-{slug}.md`** с обязательными секциями (в точном порядке):

```markdown
# E{N} — Title

> **Audience:** Product, engineering.
> **Purpose:** ...

## Summary

2–3 предложения: что пользователь сможет делать после этого epic, чего не мог раньше.

## User stories

- As a [role], I want [action] so that [outcome].
- As a ...
  (минимум 3)

## In scope

- Конкретный список возможностей (bullet points)

## Out of scope

- Что **явно** не входит (даже если кажется очевидным)

## Milestone references

- [v0.1-mvp](../milestones/v0.1-mvp.md)
- ...

## Open questions

- [ ] Вопрос 1
- [x] Вопрос 2 — решено: ...

**Status:** Not started

**Docs:** ...
```

5. **Сделай двусторонние ссылки** — в milestone тоже добавь этот epic.

---

### 3. Как писать хорошие User Stories

Формат строго:

```
As a [роль], I want [действие], so that [ценность / outcome].
```

Хорошие примеры из VenueMi-контекста:

- As an event planner, I want to upload a PDF floor plan to a venue, so that the system extracts capacity and I don’t have to type it manually.
- As a client, I want to open a pitch board link without creating an account, so that I can review venues on any device immediately.
- As a planner, I want to see confidence and provenance for every extracted field, so that I trust the data before sending it to the client.

**Плохие:**

- «Сделать API для venues» (это Technical Task)
- «Улучшить UX» (нет measurable outcome)
- «As a system, I want…» (не user-facing)

Acceptance Criteria для каждой story пишутся в milestone или в feature checklist (измеримые, testable).

---

### 4. Technical Tasks

В docs их **нет**. Они живут в трекере (Jira / Linear / GitHub Projects).

Правила хорошего Technical Task:

- Чётко привязан к одной User Story / Feature checklist item.
- Имеет Definition of Done (код + тесты + PR + обновление docs, если нужно).
- Оценим (story points или t-shirt size).
- Не содержит «и ещё…» — один task = одна завершённая единица работы.

Пример:

> Title: Implement POST /api/v1/venues + Liquibase migration for venues table  
> Story: E2 — Venue Profiles  
> DoD: API возвращает 201, схема в t_{tenant}, unit + integration tests green, OpenAPI обновлён.

### 5. Приоритизация: WSJF, RICE, MoSCoW

VenueMi уже использует **версионно-привязанные приоритеты** (P0–P3 в `feature-checklist.md`). Это удобно комбинировать с классическими методами.

#### MoSCoW (самый простой, используй на уровне Milestone / Feature Checklist)

| Категория  | Значение в VenueMi                          |
| ---------- | ------------------------------------------- |
| **Must**   | P0 — без этого нельзя выпустить v0.1 MVP    |
| **Should** | P1 — обязательно для v1.0 commercial launch |
| **Could**  | P2 — nice-to-have, можно выкинуть в v1.1    |
| **Won’t**  | P3 / Out of scope / Deferred                |

#### RICE (хорошо для product decisions)

**RICE Score = (Reach × Impact × Confidence) / Effort**

- **Reach** — сколько пользователей / deals затронет за квартал
- **Impact** — 0.25 (минимальный) … 3 (массовый)
- **Confidence** — % уверенности (50–100 %)
- **Effort** — человеко-месяцы / story points

Сортируй по убыванию score. Высокий RICE → выше в P0/P1.

#### WSJF (Weighted Shortest Job First) — лучший для Agile/SAFe

**WSJF = Cost of Delay / Job Size**

Cost of Delay обычно = User-Business Value + Time Criticality + Risk Reduction / Opportunity Enablement.

В VenueMi особенно полезен, потому что:

- Catalog (Layer 1) — enabler
- Digital Sales Room (Layer 2) — прямой buying trigger (высокий Cost of Delay)

Чем выше WSJF, тем раньше в очередь.

### Практический workflow приоритизации в VenueMi

1. Все идеи сначала попадают в **Backlog candidates** (в epics/README.md или milestones/README.md).
2. Раз в спринт/квартал:
   - Прогоняешь кандидатов через RICE или WSJF.
   - Назначаешь P0–P3.
   - Обновляешь `feature-checklist.md` (это единственный «плоский» view, по которому видно «что дальше»).
3. При создании Epic / Milestone сразу указываешь зависимости и target milestone — это автоматически задаёт порядок.

### Краткая шпаргалка «что делать прямо сейчас»

1. Хочешь новую большую фичу → проверь, что это Epic → добавь в индекс → создай файл по шаблону.
2. Хочешь маленькую user-facing штуку → добавь строку в `feature-checklist.md` с правильным Epic + Milestone + Priority.
3. Хочешь техническую работу → создай Task в трекере, привяжи к User Story / Feature.
4. Приоритизируй через MoSCoW (быстро) или RICE/WSJF (количественно).

Если нужно — могу показать конкретный пример Epic или Feature checklist item на основе текущего состояния репозитория (сейчас активен E1 Master Venue Catalog + v0.1-mvp).

**Пример интеграции: Tagvenue Scraper → Master Catalog Import → Master Catalog Venue CRUD UI (1st iteration)**

Это конкретный пример, как правильно оформить работу в рамках VenueMi-процесса (Epic → User Stories → Feature Checklist → Technical Tasks + приоритизация).

### 1. Контекст (что мы интегрируем)

По архитектуре (`master-catalog.md` + D14):

- **Tagvenue Scraper** (`mi-mc-ingest-tagvenue-scraper`) — standalone Node.js scraper. Собирает данные с Tagvenue (name, capacity, address, coordinates, pricing, photos, ratings и т.д.) → выгружает CSV/JSONL в S3 `venuemi/master-catalog/imports/{importId}/`.
- **Master Catalog Import** (`mi-mc-loader`) — Spring Boot сервис. Слушает RabbitMQ события `admin.master-catalog.import.dry-run` → `admin.master-catalog.import.apply`. Делает dry-run dedup (pg_trgm + PostGIS), генерирует audit CSV, ждёт ручного review админом, потом применяет INSERT/MERGE/SKIP.
- **Master Catalog Venue CRUD UI (1st iteration)** — в `foundation-ui-platform-admin`. Базовый список + create/edit/view + кнопки запуска import dry-run/apply. Контекст `master_catalog` (см. `ui-venue-management.md`).

Всё это относится к **Epic E1 — Master venue catalog** (Group A, target: v0.1-mvp, Status: In progress).

### 2. Как это выглядит как Epic (фрагмент)

```markdown
# E1 — Master venue catalog

> **Audience:** Product, engineering.
> **Purpose:** Platform-level reference dataset that powers autocomplete, deduplication and MC_INHERIT enrichment for tenant venues.

## Summary

Platform administrators can seed, import and manage a high-quality master venue catalog. Tenants never see it directly — they only benefit from better suggestions, fewer duplicates and richer metadata during venue creation and extraction.

## User stories

- As a PLATFORM_ADMIN, I want to run a Tagvenue scraper for a city and upload the resulting CSV/JSONL to S3, so that I can start a controlled import into the master catalog.
- As a PLATFORM_ADMIN, I want to trigger a dry-run import, review the recommended INSERT/MERGE/SKIP actions with similarity scores, and then apply the reviewed file, so that no bad data enters the catalog automatically.
- As a PLATFORM_ADMIN, I want a basic list + create/edit form for master venues (name, city, capacity, location, confidence, source), so that I can manually correct or add high-value venues in the first iteration.
- As a PLATFORM_ADMIN, I want to see aliases and external provider links (Tagvenue ID) on a master venue, so that I can understand where the data came from and prevent future duplicates.

## In scope (1st iteration)

- Tagvenue scraper (standalone) producing normalized CSV/JSONL
- S3 upload path + RabbitMQ events for dry-run / apply
- mi-mc-loader dry-run report + apply logic (human-in-the-loop)
- Basic MasterVenue list + detail + create/edit form in platform-admin UI
- Deduplication check endpoint
- Source tracking (`web_scrape`, `admin_import`, `platform_seed`)

## Out of scope (1st iteration)

- Advanced filters / bulk edit in UI
- Photo gallery management
- Automatic merge without human review
- Tenant-facing visibility of master catalog
- Other scrapers (Hire Space, HeadBox и т.д.)
```

**Общая UI-логика** в VenueMi называется так:

### Основное название

**Shared Entity Abstraction** + **Schema-driven Form** (через **Form Spec**)

Конкретно:

- **AnyVenue** — общий абстрактный тип (с дискриминатором `context: "tenant" | "master_catalog"`)
- **venue-management addon** — общий пакет/addon, в котором живёт вся переиспользуемая логика
- **Form Spec** (статический TypeScript-констант) — схема, из которой строится форма

### Как это описано в документации

Из `ui-venue-management.md`:

> Both `Venue` (tenant) and `MasterVenue` (platform) share the same canonical metadata schema and therefore the same form. Differences are handled by a single `context` discriminator — not by duplicating components.

Ключевые принципы:

- **DRY / KISS first**
- Один form spec, один набор form-компонентов, одна entity abstraction
- Shared components (`VenueProfileHeader`, `VenueProfileTabs`, `VenueFormField`, `VenueListItem`) принимают `AnyVenue` и ветвятся только там, где реально нужно

### Где это лежит

```
src/addons/venue-management/
├── types.ts          ← AnyVenue, VenueContext, VenueMetadata
├── spec/
│   ├── form-spec.types.ts
│   ├── venue-form-spec.ts
│   └── form-spec.utils.ts
└── ...
```

Этот addon шарится между:

- `foundation-ui-app` (tenant)
- `foundation-ui-platform-admin` (admin)

В админке просто передаётся `context="master_catalog"`, и tenant-only панели скрываются.

---

**Коротко:**  
Общая UI-логика = **AnyVenue + Form Spec** внутри **venue-management addon**.

**Когда общая UI-логика выносится в отдельный пакет**

По документации VenueMi (`ui-shared-packages.md`) правило очень чёткое:

### В отдельный npm-пакет (`@venuemi/ui-types`) идёт **только pure TypeScript**

Туда кладётся:

- Типы (`AnyVenue`, `VenueContext`, `VenueMetadata`, `FieldProvenance`, `ProfileStage` и т.д.)
- Константы (`PROFILE_STAGES`, `VENUE_STATUSES`, `VENUE_CONTEXTS`…)
- Type guards
- Pure utility-функции (например `computeDataConfidence()`)
- Типы Form Spec (`FieldDefinition`, `TabDefinition`…)

**Никакого React, Mantine, компонентов, CSS, form-логики.**

```
@venuemi/ui-types          ← pure TS (types + constants + pure utils)
        │
        ├── foundation-ui-app/src/addons/venue-management/     ← компоненты + form-spec
        ├── foundation-ui-platform-admin/src/addons/venue-management/
        └── foundation-ui-blank/src/addons/venue-management/
```

### Что остаётся **app-local** (в addon каждого приложения)

| Что                                                       | Почему остаётся в приложении                   |
| --------------------------------------------------------- | ---------------------------------------------- |
| `VENUE_FORM_SPEC` (конкретный spec)                       | Лейблы, порядок полей, UI-hints — app-specific |
| Все React-компоненты (`VenueFormField`, `VenueListItem`…) | Зависят от React + Mantine                     |
| `entities/venue/types.ts` (`VenueSummary`, `VenueDetail`) | DTO могут отличаться                           |
| `entities/master-venue/types.ts`                          | Только в platform-admin                        |
| API-клиенты, auth, FeatureGate                            | Разные base URL / права                        |

### Почему именно так

Приложения — **отдельные репозитории и отдельные деплои** (нет monorepo).  
Поэтому:

- Общие **контракты** (типы) → публикуются в npm как `@venuemi/ui-types`
- Общие **компоненты** → **не** публикуются (чтобы не тащить React/Mantine и не создавать жёсткую связность)

### Когда переходят на отдельный пакет

- Как только типы начинают использоваться в **двух и более** приложениях (`foundation-ui-app` + `foundation-ui-platform-admin`)
- Или когда нужно гарантировать, что `VenueMetadata`, `AnyVenue` и т.д. **не разъедутся** между приложениями

До этого момента addon можно просто копировать (как временный вариант), но официальная целевая схема — всегда через `@venuemi/ui-types`.

**Короткий ответ:**  
Общая UI-логика в отдельном пакете (`@venuemi/ui-types`) — **только когда это pure TypeScript (типы + константы + pure utils)**.  
Компоненты и form-spec остаются в app-level addons.
