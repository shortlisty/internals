## 1. Архитектура ETL-конвейера — Проверенный фундамент

### 1.1 ETL-конвейер Spring AI

Spring AI поставляет первоклассный производственный ETL-конвейер с тремя компонуемыми стадиями:

```
DocumentReader  →  DocumentTransformer  →  DocumentWriter
   (Извлечение)           (Преобразование)            (Загрузка)
```

**DocumentReaders (Извлечение) — доступные из коробки:**

| Ридер                        | Обрабатывает                                     | Примечания                                            |
| ---------------------------- | ------------------------------------------------ | ----------------------------------------------------- |
| `TikaDocumentReader`         | PDF, DOCX, XLSX, PPTX, HTML, XML, 1000+ форматов | Под капотом Apache Tika. **Основной ридер для BENE.** |
| `PagePdfDocumentReader`      | PDF, постранично                                 | Сохраняет границы страниц, полезно для планов этажей  |
| `ParagraphPdfDocumentReader` | PDF, на уровне параграфов                        | Лучший семантический чанкинг для презентаций площадок |
| `MarkdownDocumentReader`     | Markdown-файлы                                   | Полезно для структурированных спецификаций площадок   |
| `JsonMetadataReader`         | JSON с метаданными                               | Полезно для структурированного импорта                |
| `JsoupDocumentReader`        | HTML-страницы                                    | Веб-скрапинг информации о площадках                   |

**DocumentTransformers (Преобразование):**

| Трансформер                       | Что делает                                                                                                         |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `TokenTextSplitter`               | Разбивает большие документы на чанки с учётом лимитов токенов                                                      |
| `ContentFormatTransformer`        | Нормализует формат текста                                                                                          |
| `SummaryMetadataEnricher`         | Генерирует сводку документа с помощью LLM, хранится как метаданные                                                 |
| `KeywordMetadataEnricher`         | Извлекает ключевые слова с помощью LLM, хранится как метаданные                                                    |
| Кастомный `VenueMetadataEnricher` | **Специфичный для BENE Intelligence:** извлекает вместимость, удобства, контакты через структурированный вызов LLM |

**DocumentWriters (Загрузка):**

| Райтер               | Что делает                                     |
| -------------------- | ---------------------------------------------- |
| `PgVectorStore`      | Пишет чанки + эмбеддинги в PostgreSQL pgvector |
| `SimpleVectorStore`  | В памяти (тестирование/разработка)             |
| `FileDocumentWriter` | Пишет в файлы (полезно для отладки конвейера)  |

### 1.2 Конвейер обработки документов BENE

```
                     Хранилище активов S3
                          │
                          │ загрузка по подписанному URL
                          ▼
               ┌─────────────────────┐
               │  DocumentReader     │  Spring AI / Apache Tika
               │  (по типу актива)   │  + IBM Docling (таблицы PDF)
               └──────────┬──────────┘
                          │  List<Document>
                          │  (чанки сырого текста + метаданные страницы)
                          ▼
               ┌─────────────────────┐
               │  DocumentSplitter   │  TokenTextSplitter
               │                     │  (512 токенов, перекрытие 50)
               └──────────┬──────────┘
                          │  List<Document> (чанки)
                          ▼
               ┌─────────────────────┐
               │  VenueMetadata      │  GPT-4o структурированный вывод
               │  Enricher           │  → вместимость, удобства, контакты
               └──────────┬──────────┘
                          │  List<Document> + метаданные площадки
                          ▼
               ┌─────────────────────┐
               │  EmbeddingModel     │  text-embedding-3-small
               │                     │  (1536 измерений на чанк)
               └──────────┬──────────┘
                          │  List<Document> + float[] эмбеддинги
                          ▼
               ┌─────────────────────┐
               │  TenantAware        │  PostgreSQL + pgvector
               │  PgVectorStore      │  схема на тенанта
               └──────────┬──────────┘
                          │
                          ▼
               ┌─────────────────────┐
               │  MetadataAggregator │ Консолидация на основе событий
               │                     │  (разрешение конфликтов)
               └─────────────────────┘
```

**Эскиз Java-реализации:**

```java
@Service
@RequiredArgsConstructor
public class VenueAssetProcessingPipeline {

  private final TikaDocumentReader.Factory tikaFactory;
  private final TokenTextSplitter splitter;
  private final VenueMetadataEnricher enricher;   // кастомный DocumentTransformer Spring AI
  private final EmbeddingModel embeddingModel;
  private final VectorStore vectorStore;
  private final MetadataAggregationService aggregationService;

  public void process(VenueAsset asset, byte[] content) {
    // 1. Извлечь — Tika обрабатывает PDF, DOCX, XLSX, изображения через OCR, DWG
    var reader = tikaFactory.create(new ByteArrayResource(content), asset.getContentType());
    var rawDocs = reader.get();

    // 2. Обогатить сырые документы исходными метаданными
    var taggedDocs = rawDocs.stream()
      .map(doc -> doc.mutate()
        .metadata("venue_id", asset.getVenueId())
        .metadata("asset_id", asset.getId())
        .metadata("asset_type", asset.getType())
        .metadata("tenant_id", TenantContext.getCurrentTenantId())
        .build())
      .toList();

    // 3. Разбить на семантические чанки
    var chunks = splitter.apply(taggedDocs);

    // 4. Обогатить специфичными для площадки метаданными (структурированный вызов LLM)
    var enrichedChunks = enricher.apply(chunks);

    // 5. Эмбеддинг + запись в pgvector
    vectorStore.add(enrichedChunks);

    // 6. Агрегировать извлечённые метаданные в профиль площадки
    var extractedMetadata = enricher.getLastExtractionResult();
    aggregationService.applyExtractionEvent(asset, extractedMetadata);
  }
}
```

### 1.3 Матрица обработки по типу актива

| Тип актива                        | Парсер                            | Нужен OCR     | Структурированное извлечение | Индекс векторов    |
| --------------------------------- | --------------------------------- | ------------- | ---------------------------- | ------------------ |
| PDF-презентация (текст)           | Tika → ParagraphPdfDocumentReader | Нет           | Да (GPT-4o)                  | Да                 |
| PDF-презентация (отсканированная) | Tika + OCR (Tesseract)            | Да            | Да (GPT-4o)                  | Да                 |
| План этажа (PDF)                  | Docling (с пониманием вёрстки)    | Нет           | Да (зрение GPT-4o)           | Да                 |
| План этажа (изображение)          | Прямое зрение GPT-4o              | Да (LLM)      | Да                           | Да                 |
| Фото                              | Зрение GPT-4o                     | Нет           | Обнаружение удобств          | Да                 |
| DOCX / Техническая спецификация   | TikaDocumentReader                | Нет           | Да (GPT-4o)                  | Да                 |
| XLSX (таблицы вместимости)        | TikaDocumentReader                | Нет           | Структурированный парсинг    | Да                 |
| DWG / DXF (CAD)                   | AutoCAD-парсер Tika               | Нет           | Только метаданные            | Только метаданные  |
| Видео (обзор)                     | Извлечь миниатюру + аудио         | Через Whisper | Частичное                    | Частичное (Фаза 2) |

### 1.4 Стратегия чанкинга

Чанкинг документов значительно влияет на качество извлечения. BENE использует гибридную стратегию:

**Для презентаций площадок (PDF):**

- `ParagraphPdfDocumentReader`: сохраняет структуру параграфов
- Размер чанка: 512 токенов с перекрытием 50 токенов
- Метаданные на чанк: номер страницы, заголовок раздела, ID актива, уровень уверенности

**Для планов этажей (изображения/PDF с диаграммами):**

- Чанкинг на уровне страницы (один Document на страницу)
- Прикрепить полностраничное изображение для обработки зрением GPT-4o
- Извлечь: названия залов, размеры, пометки по вместимости

**Для спецификаций (таблицы):**

- Модель Docling TableFormer восстанавливает ячейки таблицы
- Каждая строка таблицы становится документом с заголовками столбцов как метаданными
- Сохраняет реляционную структуру: `{"room": "Grand Ballroom", "capacity_banquet": 400, "capacity_theater": 600}`

**Для фото:**

- Без текстового чанкинга — передать напрямую в зрение GPT-4o
- Один Document на изображение с извлечёнными зрением метаданными

### 1.5 Почему Apache Tika — правильный фундамент

Apache Tika — проверенный в боях парсер документов экосистемы Java с 2007 года:

- **1000+ форматов файлов** — единый интерфейс независимо от типа файла
- **Tika Pipes** — каждый файл обрабатывается в форкнутом JVM; неправильный или вредоносный файл не может уронить сервис
- **Проверен в производстве** — используется Elasticsearch, Solr, Apache Nutch, корпоративными поисковыми системами по всему миру
- **Поддержка DWG/DXF** — встроенный парсер формата AutoCAD (редкая возможность — большинство альтернатив этого не поддерживают)
- **Прямая интеграция со Spring AI** — `TikaDocumentReader` поставляется с Spring AI, нет необходимости в пользовательском коде
- **Нулевая облачная зависимость** — работает внутри процесса, не требуется вызов API для извлечения текста

**Конфигурация Tika Pipes для производственной безопасности:**

```java
@Bean
public TikaDocumentReader.Factory tikaReaderFactory() {
  return TikaDocumentReader.Factory.builder()
    .withTikaConfig(TikaConfig.getDefaultConfig())
    .withForkParser(true)          // Каждый файл в изолированной JVM
    .withParseTimeout(60)          // Максимум 60 с на файл
    .withMaxMemory(256 * 1024 * 1024)  // 256 МБ на файл
    .build();
}
```

### 1.6 Интеграция Docling для высокоточного парсинга PDF

Для презентаций площадок со сложными вёрстками, таблицами и многоколоночными структурами Docling превосходит базовый парсинг PDF от Tika:

**Когда использовать Docling вместо Tika для PDF:**

- Многоколоночные вёрстки (большинство презентаций площадок)
- Таблицы вместимости (настройки банкет vs. театр vs. классная комната)
- Смешанные текстовые + диаграммные страницы (планы этажей, встроенные в PDF)
- Отсканированные PDF, требующие OCR с пониманием вёрстки

**Подход к интеграции:**

```java
// Кастомный DocumentReader Spring AI, оборачивающий HTTP API Docling
@Component
public class DoclingDocumentReader implements DocumentReader {

  private final DoclingClient doclingClient; // REST-клиент к сервису Docling

  @Override
  public List<Document> get() {
    var doclingResult = doclingClient.convert(resource, ConversionOptions.builder()
      .withTableExtraction(true)
      .withOcr(resource.getContentType().contains("image"))
      .build());

    return doclingResult.getChunks().stream()
      .map(chunk -> Document.builder()
        .content(chunk.getText())
        .metadata("page", chunk.getPage())
        .metadata("element_type", chunk.getType()) // TEXT, TABLE, FIGURE
        .metadata("table_data", chunk.getTableJson())
        .build())
      .toList();
  }
}
```

**Развёртывание Docling (самохостинг, нулевая стоимость):**

```yaml
# добавление в docker-compose.yaml
docling-service:
  image: ds4sd/docling-serve:latest
  ports:
    - "5001:5001"
  environment:
    - DOCLING_WORKER_THREADS=4
```

**IBM Granite-Docling-258M** (выпущен 2026): Сверхкомпактный VLM, который преобразует документы в структурированные форматы, сохраняя вёрстку, таблицы, уравнения. Может заменить тяжёлые ML-модели Docling на более лёгкую конечную точку вывода для развёртываний, чувствительных к стоимости.

## 2. Слой интеллекта, которым владеет BENE

Всё выше (Tika, Docling, Spring AI ETL) — это инфраструктура. Собственный интеллект BENE сидит поверх:

### 2.1 Специфичная для площадок схема извлечения

Общие инструменты интеллекта документов извлекают общие поля. BENE извлекает поля, которые важны для профессионалов в сфере мероприятий:

Эта схема — то, что делает BENE _платформой интеллекта площадок_, а не просто системой хранения документов. Каждый конкурент либо имеет операционные данные (бронирования, выставление счетов), либо общее извлечение. Никто не имеет этой схемы, специально построенной для организаторов мероприятий.

### 2.2 Модель метаданных с происхождением и уверенностью

Каждое поле несёт полное происхождение:

```json
"capacity.max_total": {
  "value": 500,
  "confidence": 0.94,
  "source_type": "PDF_DECK",
  "source_page": 4,
  "extraction_model": "gpt-4o-2024-08-06",
  "alternatives": [
    { "value": 480, "confidence": 0.72, "source_type": "FLOOR_PLAN" }
  ],
  "overridden_by": null
}
```

Ни один существующий инструмент для площадок не выставляет такой уровень происхождения данных. Пользователи видят не только значение, но и _почему_ система в него верит.

### 2.3 Агрегация из нескольких источников (сложная задача, которую никто не решает)

Площадки присылают одну и ту же площадку в нескольких форматах — маркетинговая презентация, PDF с планом этажа, техническая спецификация, набор фото. Каждый источник может иметь конфликтующие или дополняющие данные.

Движок агрегации BENE:

1. Собирает все события извлечения на площадку (журнал событий)
2. Применяет правила приоритета: `manual_override > verified > high_confidence_AI > low_confidence_AI`
3. Для массивов (удобства, ограничения): объединение множеств с весом по уверенности
4. Выставляет конфликты в UI: «ИИ нашёл два разных значения вместимости — какое правильное?»
5. Позволяет разрешение в один клик

Это подлинный продуктовый ров. Ни одна другая платформа в сфере мероприятий этого не делает.

## 3. Архитектура масштабируемости

### Событийно-управляемая, горизонтально масштабируемая

```
Загрузка → S3 → AssetUploadedEvent → RabbitMQ → N потребителей → Конвейер обработки
                                                    ↑
                                              Масштабировать потребителей
                                              по глубине очереди
```

- Каждое задание извлечения независимо — N воркеров могут работать параллельно
- Приоритетные очереди по уровню тарифа (Enterprise обрабатывается первым)
- Очередь мёртвых писем ловит сбои — автоматический повтора с задержкой
- Нет единой точки отказа в пути обработки

### Стоимостное масштабирование

| Масштаб            | Стоимость ИИ | Инфраструктура                                        |
| ------------------ | ------------ | ----------------------------------------------------- |
| 100 площадок (MVP) | ~$0.10       | Одиночный контейнер                                   |
| 10K площадок       | ~$10         | 2-3 контейнера                                        |
| 1M площадок        | ~$1,000      | Автомасштабируемый, всё ещё управляемый               |
| 100M площадок      | ~$100K       | Оптимизировать более дешёвыми моделями + кэшированием |

При стоимости GPT-4o извлечения + генерации эмбеддингов $0.001/площадку BENE может обработать 1 миллион площадок примерно за $1000 стоимости ИИ. Это не проблема стоимости.

### Масштабирование векторного поиска

pgvector с индексом IVFFlat:

- Семантический поиск менее чем за 10 мс при 1M площадок
- Масштабируется до ~5M векторов на экземпляр перед потребностью в оптимизации (индекс HNSW или облачный Pgvector)
- Мультитенантная изоляция через схема-на-тенанта — нет межтенантных утечек данных

## 4. Сводка технологических решений

| Слой                      | Выбор                                              | Обоснование                                                                               |
| ------------------------- | -------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| **Парсинг документов**    | Apache Tika (через Spring AI `TikaDocumentReader`) | 1000+ форматов, поддержка DWG, отказоустойчивые Pipes, встроено в Spring AI               |
| **Анализ вёрстки PDF**    | IBM Docling (самохостинг, open source)             | Передовое извлечение таблиц/вёрстки, лицензия MIT, нулевая стоимость за страницу          |
| **AI-фреймворк**          | Spring AI 1.0                                      | Нативный для Java, независимый от провайдера, встроенный ETL-конвейер, метрики Micrometer |
| **LLM извлечение**        | OpenAI GPT-4o                                      | Лучший структурированный вывод, мультимодальный (зрение для изображений/планов этажей)    |
| **Эмбеддинги**            | OpenAI text-embedding-3-small                      | 1536 измерений, $0.02/1M токенов, отличное соотношение качество/стоимость                 |
| **Векторное хранилище**   | pgvector (расширение PostgreSQL)                   | Нет доп. сервиса, транзакционный, изоляция по тенантам, готовый к производству            |
| **Полнотекстовый поиск**  | PostgreSQL tsvector                                | Унифицирован с реляционными данными, нет доп. сервиса                                     |
| **Геопоиск**              | PostGIS (расширение PostgreSQL)                    | Зрелый, нет доп. сервиса                                                                  |
| **Асинхронная обработка** | RabbitMQ (существующий фундамент)                  | Уже в платформе, приоритетные очереди, DLQ                                                |
| **Файловое хранилище**    | S3 / MinIO (существующий фундамент)                | Уже в сервисе IAM, тот же паттерн                                                         |

**Принцип:** Использовать проверенную инфраструктуру, которая уже существует в фундаменте IQ Key Value. Вводить минимальное количество новых сервисов. Единственная действительно новая инфраструктура — это pgvector (расширение PostgreSQL, не новый сервис) и опционально самохостящийся контейнер Docling для продвинутого парсинга PDF.

## 5. Открытые вопросы для реализации

- **Docling vs. чистый Tika:** Начать с Tika для скорости MVP. Добавить Docling для Фазы 2, когда станет важна точность планов этажей.
- **Стратегия OCR:** Tika включает Tesseract для базового OCR. Зрение GPT-4o обрабатывает сложные случаи. Порог: если уверенность OCR Tika < 0.7, эскалировать до зрения GPT-4o.
- **CAD-файлы:** Tika извлекает метаданные из DWG/DXF (размеры, слои). Для Фазы 1 выставлять сырые метаданные. Фаза 2: конвертировать в PNG через LibreCAD/ODA, затем зрение GPT-4o для понимания вёрстки.
- **Видео-обзоры:** Вне скоупа Фазы 1. Фаза 2: извлечь ключевые кадры (ffmpeg), запустить зрение GPT-4o на репрезентативных кадрах.
- **Перекрытие чанков:** перекрытие 50 токенов — стандарт. Контент, специфичный для площадок (например, таблицы вместимости), должен использовать меньшие чанки (256 токенов) для сохранения построчной точности.
- **Свежесть эмбеддингов:** Пере-эмбеддинг, когда ручные перезаписи изменяют консолидированные метаданные. Запуск через `MetadataAggregatedEvent`. Не пере-эмбеддинг неизменённых чанков.
