# v1.1 — Agency knowledge base

> **Audience:** Product, engineering.
> **Purpose:** Define the scope, acceptance criteria, and deferred items for the Agency Knowledge Base milestone — the first post-v1.0 capability extension.

---

## Goal

An agency can capture and reuse its operational knowledge — SOPs, event retrospectives, reusable templates, and a vendor registry — without leaving Shortlisty.

## Acceptance criteria

1. An agency owner can create an SOP with at least three steps, attach it to a Deal Room, and a teammate can tick steps independently — progress is reflected in real time for all tenant members.
2. A planner can submit a retrospective for a completed event linked to a venue; the venue's profile page surfaces that retrospective under "Past experience" and it is not visible on any client-facing page.
3. A coordinator can apply a Brief template to a new project and receive an independent copy whose edits do not propagate back to the master template.
4. A planner can add a vendor with Preferred status, write a performance note linking to a retrospective, and find that vendor via a category + rating filter in under 30 seconds.
5. A viewer-role user can browse SOPs, retrospectives, templates, and the vendor registry but cannot create, edit, or delete any record.
6. None of the knowledge-base records (SOPs, retrospectives, templates, vendor notes) are accessible from any client-facing pitch board link.

---

## Deferred items

- Automated SOP triggering by Deal Room stage or event type (requires a workflow engine not present in v1.1 — backlog candidate for v1.2).
- AI-assisted retrospective summarisation and pattern detection across multiple events (post-v1.1).
- Client-shareable brief intake form generated from a Brief template (significantly extends scope — explicit product decision required before adding).
- Cross-tenant template sharing or a public template marketplace (out of scope for v1.1 per D17).
- Vendor recommendations surfaced inside client-facing Deal Rooms (crosses internal/external boundary — requires explicit product decision).
- Retrospective outcome signal feeding into search ranking (requires search layer changes — revisit post-v1.1).
- SOP and template version history / change tracking (deferred to v1.2).
